Reverse-Engineering a Home Audio System

One control surface for six zones, three devices, and three protocols that don't talk to each other

A personal hardware project, built mostly by AI coding tools with me correcting them in the loop. The parts that held up were the ones with a clear pattern to follow; the parts that broke were every place the code needed to know something only the physical devices could tell it.

  • Protocol reverse-engineering
  • Marantz · AudioControl · HEOS
  • FastAPI control UI
  • Raspberry Pi
  • AI-assisted build

Why this exists

The setup: two Marantz SR5014 AV receivers and an AudioControl M4800 four-zone amplifier, six audio zones across the house. Every device has its own web interface, and none of them know the others exist. The M4800's control API is undocumented. Streaming state — what's actually playing in a room right now — lives in a third protocol (HEOS) that neither web interface exposes cleanly. I wanted one always-on page that could see and drive every zone, running on a Raspberry Pi in the rack.

This one predates the rest of my portfolio's "hardware plus software" framing, but it's still the clearest single example of those layers meeting in one place: real consumer AV hardware, real protocol work to make it controllable, and a build process that leaned hard on AI coding tools with a human catching what they got wrong.

Recovering the M4800's API from its own web UI

The AudioControl M4800 has a browser-based control panel but no published API. So I treated the web panel as the spec: pulled its JavaScript bundle and traced what its own controls do on the network. Underneath, it's a small JSON API:

  • GET / POST json/operation.json — device and per-zone status, and every control command
  • realTimeData.json, configuration.json, signalprocessing.json — monitoring, config, and DSP state

Then I wrote down the command grammar the panel posts as URL-encoded form fields: outputZone_<n>_zonePower (0/1), _mute (0/1), _trim (−10…+10), and _inputSource (0–8, mapping to four analog channel pairs, four digital inputs, and a pink-noise generator). Once that grammar was documented, a from-scratch audiocontrol_controller.py could do everything the web panel could — power, volume, mute, and source routing per zone, plus temperature telemetry.

Three protocols, one surface

Each device speaks something different, so the control layer is really three adapters behind one interface:

  • Marantz SR5014 — driven through the denonavr library; Denon and Marantz share a control protocol, so that part was a solved problem.
  • AudioControl M4800 — the from-scratch controller built on the reverse-engineered JSON API above.
  • HEOS — a separate TCP protocol on the Marantz receivers, used only to read "now playing" metadata that the receiver's own web UI doesn't surface.

A FastAPI backend (api_server.py) pulls all three together behind a single dark-themed web page: power, per-zone volume/trim, mute, source routing, and temperature across all six zones. A Streamlit version came first and was replaced by the FastAPI one once the UI needed more control than Streamlit wanted to give.

How it was actually built

This was a vibe-coding project, and I'll be straight about that. Most of the code was generated by AI coding tools from a running description of the hardware and what I wanted. That worked well for the parts with a clear shape — HTTP calls, a status page, form handling, wiring three controllers behind one router. It fell down in exactly the place you'd predict: anywhere the code needed a fact that only the physical devices could provide. The model would produce something that read as correct, compiled, and passed a glance — and then behaved nothing like the rack did.

The SETUP_LOG.md in the repo is one line long, and that's the honest artifact of this build. The real debugging didn't happen in a document — it happened live, at the rack, with me comparing raw JSON responses against what the front panels were actually showing and feeding the corrections back in.

Real moments from the build

Every one of these is a genuine bug found by running the thing against the actual hardware, not by reading the code.

Confident code, silent hardware

HEOS "now playing" timed out on every zone

The HEOS controller timed out fetching now-playing metadata — roughly two seconds per zone — so station names came back empty and the whole page took five to ten seconds to load, because it queried all six zones one after another. The generated code was structurally reasonable; it just assumed a HEOS connection that behaved the way the model expected rather than the way the receivers actually did. The fix path was a real reconnect strategy and parallel polling, not a tweak to the request.

The API said yes; the amp disagreed

Every zone reported powered-on at startup

The M4800 status read came back with all four zones showing power-on regardless of their real state, so the UI toggles started out of sync with the rack. Catching it meant reading the raw operation.json payload against what the amplifier's front panel actually displayed — the kind of check the code generator had no way to do.

Reading the wrong number

Volume came back as 0 for every zone

The M4800 reports level as a trim value in the −10…+10 range. The generated code was reading a separate volume field that was always 0, and the slider was bound to that field. Everything looked wired up; the number was just coming from the wrong key. Only visible by diffing the JSON against what the zones were doing.

A dependency that couldn't coexist

asyncio==3.4.3 pinned in requirements

The generated requirements.txt pinned asyncio as a package — a backport that conflicts with the standard library's built-in asyncio on any modern Python and breaks the install outright. The fix was deleting one line; nothing in the code needed it. A small thing, but a representative one: the model reached for a dependency that hadn't been necessary for years.

What it's built on

Python throughout. denonavr for the Marantz receivers, requests against the reverse-engineered M4800 JSON API, and a raw-TCP HEOS client for streaming metadata. FastAPI plus a single hand-written HTML page, no frontend framework. The reverse-engineering itself was done with requests and BeautifulSoup against the M4800's own web panel and its JavaScript bundle. It runs on a Raspberry Pi as an always-on service on the home network.

What would separate this from a working personal project: parallelized zone polling, since the sequential loop is the main source of latency; a real HEOS reconnect strategy instead of per-call timeouts; and device auto-discovery instead of hard-coded addresses. None of that is here — it's the honest list of what "solid" would still cost.
